# NEIRA frontend

SPA на React, Vite и TypeScript. Регистрация, вход, восстановление сессии, выбор workspace, приглашения, управление участниками и внутренние уведомления подключены к backend. Каналы пока остаются демонстрационным интерфейсом без серверной интеграции. Старый кабинет и добавленный пример Miro в корне рабочей папки служат источниками дизайна и структуры; их старые обходные решения сюда не переносились.

## Запуск и проверки

Нужны Node.js >=22.22 и Yarn 1.22.22. Из `frontend/`:

```sh
yarn install --frozen-lockfile
yarn dev
yarn typecheck
yarn lint
yarn format:check
yarn build
```

`yarn format` форматирует проект, `yarn lint:fix` исправляет доступные ESLint-ошибки.

Vite проксирует `/api` на `http://127.0.0.1:8000`. Для локальной авторизации открывай frontend по `http://localhost:5173`: этот адрес должен совпадать с `FRONTEND_ORIGIN` backend. Для регистрации и входа нужен запущенный backend с применённой миграцией и PostgreSQL.

## Структура

Используем три слоя:

- `src/app/` — сборка приложения, маршруты, провайдеры, i18n и глобальные стили;
- `src/features/` — бизнес-модули `auth`, `settings`, `channels`, `funnels`, `workspaces`, `members`, `invitations`, `notifications`, `dashboard-layout`, `not-found`, `error-boundary`, `change-language` и `change-theme` с их UI, состоянием, запросами и переводами;
- `src/shared/` — Axios-инстансы и интерцепторы, сгенерированные OpenAPI-типы, UI-примитивы и общие утилиты.

`app` собирает модули из `features`; модули используют `shared` и при необходимости публичный `index.ts` другого модуля без циклических импортов. Внутри модуля используются относительные импорты. `LanguageSwitcher` находится в `features/change-language`, базовые поля, кнопки, карточки и логотип — в `shared/ui`.
ESLint проверяет направление импортов между слоями и запрещает обход публичного API другого модуля.

Короткие обязательные правила размещения кода и данных записаны в [`AGENTS.md`](AGENTS.md).

Маршруты объявлены в `src/app/router.tsx` через `createBrowserRouter`, а `RouterProvider` подключён в `src/app/main.tsx`. `/` перенаправляет на `/settings` через loader. Гостевая и защищённая проверки читают одно состояние из `AuthProvider`; визуальные лаяуты не проверяют доступ. Защищённая ветка сначала проверяет вход. Для workspace-зависимых страниц требуется выбранное пространство; `/notifications` доступен авторизованному пользователю и без членства в workspace. `/auth/select-workspace` собирается в `features/workspaces` и использует общий auth-лаяут. Публичный `/invites/:token` открывает приглашение до входа и возвращает пользователя к подтверждению после авторизации; регистрация по приглашению сразу добавляет его в указанное пространство. Ветка каналов отдельно подключает демонстрационные данные. Экраны загружаются через `lazy`, а `*` показывает 404. Общий загрузочный экран показывается при начальной инициализации и во время навигации. Обработчики ошибок маршрутов, рендера и инициализации находятся в `features/error-boundary` и подключаются в `app`. При публикации SPA сервер должен отдавать `index.html` для frontend-маршрутов, чтобы они открывались напрямую.

Цепочка восстановления входа: `main.tsx` → `router.tsx` → `Providers` → `useQuery` в `AuthProvider` → при необходимости `/auth/refresh` → `/auth/me`. `Providers` устанавливает auth-интерцепторы до монтирования `AuthProvider`. Запрос запускается при монтировании провайдера, в том числе на странице входа; маршрутные проверки только читают его результат. HTTP 401 означает отсутствие сессии; временная ошибка сети или сервера показывает экран с повторной попыткой. После регистрации и входа `AuthProvider` также получает `/auth/me` и записывает пользователя в тот же кэш. Формы только вызывают login/register; `GuestOnlyRoute` выполняет переход в кабинет или к выбору workspace и сохраняет исходный защищённый адрес. Если refresh перестал работать уже после входа, клиент очищает токен и провайдер сбрасывает кэш. Данные `/auth/me` нужны для входа в кабинет и проверки членства в workspace; подписка, баланс и другие предметные данные не добавляются в auth-провайдер.

Компоненты в `shared/ui` стилизуются через Tailwind; `Button` поддерживает `asChild` через Radix Slot, `Badge` задаёт общие статусные плашки, мобильное меню и окно смены пароля используют Radix Dialog с порталом, а выбор языка и темы — Radix Select с порталом списка. Цвета компонентов берутся из семантических токенов в `src/app/index.css`. Там заданы светлая и тёмная палитры по макету; для нового элемента сначала добавляй или переиспользуй токен, а не указывай цвет в компоненте. Начальная тема выбирается по сохранённому `neira.theme` или настройке системы до первого рендера, ручной выбор сохраняется и меняется через `features/change-theme`.

Боковое меню кабинета на широком экране сворачивается до 80 px. Кнопка на его границе появляется при наведении и при фокусе с клавиатуры; выбор сохраняется в `neira.sidebar-collapsed`. Нижняя карточка аккаунта раскрывается отдельно, плавно сворачивается с учётом `prefers-reduced-motion` и сохраняет своё состояние при переключении вида меню в рамках открытого приложения. На мобильном экране меню остаётся полноразмерным в выдвижной панели.

Формы входа и регистрации используют `features/auth/api/auth-api.ts`. `shared/api/client.ts` создаёт Axios-инстансы с общим базовым URL и передачей cookie; запросы к конкретным endpoint там не размещаются. `shared/api/auth-interceptors.ts` хранит access token в памяти, добавляет его и выбранный workspace в запросы и выполняет один refresh для одновременных ответов 401. `app/providers.tsx` передаёт интерцепторам функцию refresh из `features/auth`. Регистрация проверяется Zod и содержит два обязательных согласия с офертой и обработкой персональных данных. Ссылки на оферту и политику ведут на публичный сайт NEIRA, а документ согласия раздаётся из `public/`. Подтверждение email кодом пока не выполняется; `/auth/verify` остаётся демонстрационным экраном для будущего этапа.

Backend возвращает короткоживущий access JWT в ответе и хранит refresh JWT в HttpOnly cookie. Access-токен остаётся только в памяти вкладки; при обновлении страницы `AuthProvider` получает новый access-токен через `/api/v1/auth/refresh` и загружает `/api/v1/auth/me` через React Query. Одновременные запросы после 401 используют один refresh и повторяются один раз. В `localStorage` хранится только идентификатор выбранного workspace. При одном membership workspace выбирается автоматически; при нескольких после входа показывается список. После обновления страницы сохранённый ID принимается только если он есть в актуальном `/auth/me`. Workspace можно сменить в настройках без повторного входа. Для tenant-scoped запросов передавай `workspace: true` в конфигурации Axios: auth-интерцептор добавит `X-Neira-Workspace-Id`, а backend проверит членство. После смены workspace сбрасывай или ключуй tenant-scoped кэш; демонстрационные каналы уже сбрасываются при переключении. `logout()` завершает серверный сеанс и очищает локальное состояние. Если сервер недоступен, локальное состояние очищается, но серверный отзыв cookie подтвердить нельзя: UI показывает предупреждение.

`NotificationStream` в `Providers` подписывается на `/api/v1/notifications/stream` только при активном входе. SSE-запрос использует текущий Bearer access token из памяти, на 401 пробует общий refresh и повторяет подключение. После штатного закрытия соединения сервером через 60 секунд или сетевого сбоя клиент переподключается с ограниченной задержкой; при выходе подписка отменяется. События `connected` и `invalidation` запускают обновление `/auth/me` и приватных данных React Query. Redis Pub/Sub не хранит пропущенные события, поэтому каждое новое подключение сверяет состояние с PostgreSQL через обычные API-запросы.

Уведомления принадлежат пользователю, поэтому их ключи React Query включают `userId`, а страница доступна и без выбранного workspace. Список загружается курсорными страницами по 50 записей; следующая страница запрашивается кнопкой «Показать ещё». В состоянии без пространств экран выбора даёт ссылку на уведомления, чтобы приглашение оставалось доступным.

Экран настроек показывает имя, email, Telegram, аватар и членства в workspace из `/api/v1/auth/me`. Если `avatar_url` пустой, вместо фото показывается инициал; если Telegram не указан, показывается «—». Раздел пространств содержит текущее пространство, участников со счётчиком и список пространств. Диалоги позволяют переименовать пространство, управлять участниками и приглашениями, переключить пространство без повторного входа. Диалог «Активные сеансы» загружает реальные устройства и позволяет завершить отдельный другой сеанс или все остальные сразу; его endpoint-функции и React Query-логика находятся в `features/settings`. В кабинете можно изменить пароль, введя текущий и новый; неверный текущий пароль показывается у поля, а после успешной смены другие сеансы завершаются. Восстановление забытого пароля пока не реализовано. Редактирование имени, Telegram и аватара остаётся явным UI-предпросмотром без серверного сохранения. Выбранное фото остаётся локальным `File` с временным object URL; оно не записывается в серверное поле `avatar_url`.

Страницы каналов показывают образцы из макета: список с поиском и фильтром, состояния соединения, выбор типа подключения, боковую инструкцию и экран редактирования. В мастере подготовлены формы Telegram Premium, Telegram Bot, Telegram Personal, MAX, Instagram и Facebook; WhatsApp Official, Jivo и VK пока показывают честное состояние без формы, поскольку их детальные сценарии не подтверждены макетом. `sampleChannels` задаёт начальные данные `ChannelsPreviewProvider` только в ветке маршрутов каналов. Список и страница канала читают один массив: изменения после подтверждения в списке и после сохранения на странице редактирования сразу видны в обоих экранах, а удалённый канал больше не открывается. Черновик формы до сохранения остаётся локальным. Демо-изменения хранятся только в памяти ветки каналов и сбрасываются при переходе в другой раздел или перезагрузке; действия не подключают, не проверяют и не удаляют реальные каналы. API каналов, постоянное хранение и адаптеры интеграций появятся вместе с согласованным пользовательским сценарием.

Адреса существующих страниц хранятся в `src/shared/config/routes.ts`. Динамический маршрут `/channels/:channelId` строится через `channelDetailsPath()` и `generatePath`; `useParams<"channelId">()` возвращает возможное отсутствие параметра, а страница проверяет, существует ли такой канал. В текущем режиме Data Router React Router не связывает тип параметра с записью маршрута автоматически. Для следующих динамических маршрутов сохраняйте явную проверку параметров и данных во время выполнения.

## Управление workspaces

При обычной регистрации создаётся `My Workspace`; регистрация по приглашению добавляет пользователя только в приглашённое пространство. В настройках показываются текущее пространство и число доступных пространств. Кнопка «Управлять» открывает модальное окно с текущим и остальными пространствами: можно переключаться, создавать новые, переименовывать пространства с ролью владельца или администратора и удалять другие собственные пространства. Удаление текущего пространства через интерфейс недоступно. Если пользователь потерял последнее членство из-за удаления пространства другим владельцем, экран выбора показывает название удалённого пространства из `/auth/me` и предлагает создать своё. Профиль и сеансы при удалении пространства сохраняются.

Операции workspace принадлежат `features/workspaces`, а управление участниками и приглашениями — `features/members`. Список доступных пространств для выбора берётся из `/auth/me`; после успешной операции этот кэш обновляется из ответа API. При смене текущего workspace приватные данные прежнего контекста сбрасываются. Создание, переименование и удаление выполняются через `/api/v1/workspaces`; backend также предоставляет отдельный `GET /api/v1/workspaces`. Роли членства — `owner`, `admin`, `manager` и `reader`; права проверяет backend.

## Воронки

Страница `/funnels` находится в основном разделе меню и показывает воронки выбранного workspace. Данные загружаются с backend через `features/funnels/api` и React Query; ключ кэша начинается с `private` и включает `workspaceId`. Текущие роли позволяют изменять воронки только владельцу пространства. Переключение workspace меняет выбор и данные доски.

Каждая воронка показывает статусы колонками в порядке сервера; входящий статус всегда первый. Доска занимает доступную высоту и с пустыми колонками, а горизонтальная прокрутка дополнена полупрозрачными кнопками у краёв. Выбор воронки, режимы просмотра, поиск и меню настроек находятся в контенте страницы; кнопка создания обращения — в верхнем заголовке. Колонки отделены от панели управления линией с отступами и друг от друга мягким пунктиром; их заголовки окрашены по сохранённому цвету статуса, а описание доступно через значок вопроса. Пустые колонки показывают ноль обращений, поскольку сущность обращений пока не реализована. Режим таблицы, поиск и кнопки создания обращения видны, но пока не выполняют эти действия.

Меню с шестерёнкой открывает создание, настройку и удаление воронки. При создании новая воронка получает редактируемый набор из пяти статусов. В том же диалоге настройки можно изменить имя, описания, цвета и порядок статусов, добавить или удалить этапы; весь набор сохраняется одним запросом. CSS-токены задают цвета в светлой и тёмной темах. На доске вторичные статусы переставляются через dnd-kit за любую свободную область заголовка мышью, касанием или клавиатурой; входящий этап меняется отдельным действием. Подсказки описания и входящего индикатора выводятся через Radix Tooltip рядом с соответствующими иконками поверх прокручиваемой доски. Запросы выполняются через tenant API с `X-Neira-Workspace-Id`.

## Типы API

При запущенном backend команда ниже получает `/openapi.json` и обновляет `src/shared/api/generated/schema.ts`:

```sh
yarn api:generate
```

Можно указать другой URL или путь к локальному JSON/YAML-файлу: `yarn api:generate ./schema.json`. Генератор использует `openapi-typescript`; текущая схема содержит health, auth, sessions, workspaces, участников, приглашения, уведомления и воронки. Сгенерированный файл не редактируется вручную. Для проверки ввода регистрации и ответа `/me` используется Zod; OpenAPI-типы сами по себе runtime-валидацию не выполняют.

## Переводы

Приложение использует `i18next` и `react-i18next` с локальными словарями. Поддерживаемые языки, русский fallback и ключ хранения выбора находятся в `src/shared/i18n/languages.ts`. При запуске язык берётся из сохранённого ручного выбора, затем из настроек браузера; если подходящего перевода нет, используется русский. Автоматически определённый язык не сохраняется. Переключатель сохраняет ручной выбор и обновляет `html lang` и `dir`.

Строки интерфейса размещай рядом с их владельцем: например, переводы 404 лежат в `src/features/not-found/i18n/translations.ts`. Для нового модуля добавь словари `ru` и `en`, экспортируй их через `index.ts`, зарегистрируй namespace в `src/app/i18n/resources.ts` и используй `useTranslation('namespace')` в компонентах. Русский словарь задаёт ключи; TypeScript проверяет их наличие в английском. Общие строки приложения хранятся в `src/app/i18n/translations.ts`. Название продукта и технические идентификаторы не переводятся.

Сейчас словари включены в сборку. Сетевой загрузчик переводов не нужен, пока объём словарей или способ управления ими не потребует отдельного решения.
